# 第一版实现说明

本文记录需求与当前代码的对应关系，便于继续迭代和验收。

## 三端

| 需求 | 实现 |
| --- | --- |
| 用户浏览 | `/api/v1/catalog` 只返回启用、未删除商家的有库存在售商品 |
| 用户导购 | 用户端文本/麦克风输入，双 WebSocket 接收卡片、理由、完整文本和音频 |
| 用户订单 | 创建待确认订单并确认/取消，只查询当前用户订单 |
| 商家 CRUD | 店铺与商品创建、更新、软删除；所有 SQL 按 owner 约束 |
| 商家订单 | 通过店铺 owner 关联，只返回当前商家的订单 |
| 平台治理 | 全量商家/商品/订单，以及必须填写原因的商家禁用 |
| 品类治理 | 平台维护一级/二级品类及必填、选填槽位；商家按二级品类动态建品 |

## Agent 工作流

`intent_agent → clarification_agent → catalog_retrieval → recommendation_agent → emotional_agent → compliance_check`
由 LangGraph 条件边驱动。订单意图路由到图内订单事务节点，再进入合规检查。

- 意图识别读取当前话语和最近三轮消息，并把 `category_l2` 中全部二级分类的必填、选填
  槽位动态注入 System Prompt，输出单个标准意图、置信度和订单 action。
- 澄清规则从平台品类表加载必填槽位；先抽取当前话语已有信息，再询问前一到两个缺失槽位。
- 仅当需求澄清返回 `READY` 后，商品召回节点用单条 SQL 过滤+排序：品类、预算与**全部已填
  槽位（含可选槽位）**拼成硬过滤条件，再使用 1024 维查询向量按 PGVector 余弦距离截取
  Top 20（向量不可用降级为 `created_at` 排序）。
- 推荐节点分两阶段：先按 `qwen3-rerank` 精排取 Top 3，再用画像快照规则（品牌偏好 +0.2、
  超价 > 1.5 倍客单价 -0.15、最近复购 -0.3）在 Top 3 内部二次排序，输出商品卡与
  `matchScore`（精排分 + 规则分）及逐项 `scoreBreakdown`。
- 商品向量在商品创建/更新时生成：结构化字段先拼成带中文标签的"商品卡片"（品类、槽位、
  枚举值均映射为中文），调用 `qwen3.7-text-embedding` 后归一到单位向量再入库；
  向量化失败降级为空，召回侧回退到词法匹配。
- 推荐节点只产生商品卡和情绪风格；情感节点为每个事实商品产生一条理由和完整话术。
- 增量推送和完整话术都经过正则规则；完整命中时改为固定兜底文本，不再提交原文 TTS。

未配置模型密钥时，同一契约使用确定性实现，便于离线开发和测试。

## 品类与商品校验

`category_l1` 独立保存一级分类，`category_l2` 保存二级分类并通过外键关联一级分类，
`category_slots` 保存二级分类槽位、必填标记和非空 JSON 枚举数组。平台 API 按“一级分类 →
二级分类 → 槽位”三步创建，并在数据库和请求模型两层阻止孤立二级分类及空枚举槽位；商家端
选择二级分类后自动带出一级分类，并根据槽位枚举生成选择控件。

商品创建和品类/属性更新会在 API 侧重新读取当前槽位定义：校验一二级归属、品类启用状态、
未知槽位、枚举范围以及所有必填项，校验通过后才写入 `products.attributes`。

## 订单与画像

待确认订单保存商家/商品成交快照、当前价格、数量、总金额、十五分钟过期时间和幂等键。
确认时锁定订单、商品和商家记录，复核可售性、价格及库存；成功后原子扣减库存并更新为
`success`。取消、超时或校验失败进入 `fail`，终态不可迁移。

商品点击和成功订单都更新静态/动态画像；订单增量高于点击。推荐轮次开始时生成只读画像快照，
并与 `ShoppingState` 一起保存在 `session_states`。

## 仍需生产化的边界

- 当前身份请求头仅用于演示，需要接入认证、角色授权和密码登录。
- 合规关键词、品类槽位和画像衰减参数需要由业务团队最终确认。
- 生产部署需使用业务空间专属模型域名、集中密钥管理、限流、指标告警和数据库迁移工具。
- 当前版本按需求不实现支付、退款、物流和售后。
