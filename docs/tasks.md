# 语音导购 Agent 任务文档

本文将需求、架构和实现说明转换为可执行的开发任务，记录当前 MVP 基线、后续迭代顺序、任务依赖和验收标准。任务状态以代码和测试为准，需求变更后需要同步更新本文及相关设计文档。

## 1. 当前基线

当前 MVP 已完成以下端到端能力，作为后续任务的共同起点：

- 三端前端和 FastAPI 模块化单体后端的基本业务闭环。
- LangGraph 意图识别、需求澄清、商品推荐、订单处理、情感应答和合规检查流程。
- 动态品类、槽位枚举、商品属性校验和基于 SQL 的硬过滤。
- PGVector 召回、Reranker 精排、画像二次排序和确定性降级。
- 待确认订单、幂等创建、锁行确认、价格/库存复核和成交快照。
- 文本/音频 WebSocket、ASR、TTS、事件序号、Redis 重放和会话状态持久化。
- 静态画像候选收敛、动态行为画像和基础 LangSmith trace。

基线验证命令：

```bash
pnpm typecheck
pnpm build
pnpm test:api
pnpm lint:api
```

## 4. 生产上线前任务

### TASK-001：接入真实认证和角色授权

- 优先级：`P0`
- 状态：`TODO`
- 目标：替换请求头演示身份，为 HTTP API、文本 WebSocket 和音频 WebSocket 建立统一身份认证与授权链路。
- 影响范围：`core/identity.py`、各模块 router、`realtime/router.py`、配置和前端登录态。
- 依赖：确定身份提供方、token 格式和平台端角色模型。
- 实施要点：
  - 保留本地 `demo` 模式，但必须由显式配置开启，生产配置禁止回退到固定用户。
  - HTTP 请求从已验证凭证解析 `user_id`、角色和商家归属，不能信任客户端传入的 owner ID。
  - WebSocket 在握手阶段完成 token 校验，并在连接存续期间绑定用户和 session。
  - 平台接口、商家资源和用户订单分别增加 `401/403` 行为约束。
- 验收标准：未认证请求全部被拒绝；商家不能访问其他商家数据；普通用户不能访问平台接口；WebSocket 鉴权失败不会建立业务连接；所有边界有 API 和 WebSocket 测试。

### TASK-002：将句子级合规检查前移为 TTS 闸门

- 优先级：`P0`
- 状态：`DONE`
- 目标：确保任何发送给 TTS 的文本都已经通过短句级合规检查。
- 影响范围：`agents/graph.py`、`agents/nodes/response.py`、`agents/service.py`、`realtime/tts.py` 及相关测试。
- 依赖：无。违规时统一进入 `violation_response`，播报固定违规提示。
- 实施要点：
  - 保留逐卡理由和文本增量过滤，作为流式展示的第一道保护。
  - 完整话术生成后由 `compliance_check` 按短句逐一检查，通过后才调度 `speech_sentence_publisher`。
  - 任一短句违规时跳转 `violation_response`，不得继续使用原始话术进行文本或 TTS 发布。
  - 文本、持久化回复和音频统一使用固定违规提示。
  - 维持 `audio.start/audio.end/audio.done` 的顺序和断线行为。
- 验收标准：包含禁用表达的短句不会触发原文 TTS；工作流进入 `violation_response`；固定违规提示可以正常播报；文本流、持久化回复和音频内容一致；测试覆盖短句边界、违规路由和发布顺序。

## 5. 下一迭代任务

### TASK-003：将商品向量重建改为异步批处理

- 优先级：`P1`
- 状态：`TODO`
- 目标：避免平台端同步重建在商品量增加后阻塞请求或超时。
- 影响范围：`modules/platform/router.py`、`core/product_embedding.py`、`core/embeddings.py`、数据库 schema、任务执行器和平台端。
- 实施要点：
  - 创建可查询的重建任务记录，返回任务 ID 和初始状态。
  - 按批次读取需要重建的商品，支持限流、重试、失败记录和继续执行。
  - 根据商品事实字段变更判断是否需要重算，重复提交同一范围必须幂等。
  - 平台端展示总量、成功数、失败数、最后错误和完成时间。
- 验收标准：重建请求快速返回；任务可暂停/失败/完成并可查询；单个商品失败不阻塞整个批次；重复任务不会产生并发写入冲突；重建后的向量可被推荐链路使用。

### TASK-004：统一品类槽位和合规规则配置

- 优先级：`P1`
- 状态：`TODO`
- 目标：消除数据库品类配置、应用常量和提示词之间的漂移，并让合规规则可审计。
- 影响范围：`core/taxonomy.py`、`agents/nodes/constants.py`、Agent prompts、平台端配置 API、schema 和缓存。
- 实施要点：
  - 明确槽位类型、枚举值、问题文案、匹配语义和版本号的唯一来源。
  - 配置发布前校验必填槽位、枚举非空、键名和匹配器是否兼容。
  - 配置变更记录操作者、变更前后内容和生效时间，并支持回滚。
  - 同一轮工作流使用固定配置快照，避免提示词、校验器和 SQL 条件读取到不同版本。
- 验收标准：新增或修改槽位无需修改多处常量；非法配置无法发布；配置变更可追溯和回滚；缓存失效后新会话使用新版本，进行中的 turn 使用原快照。

### TASK-005：完善生产可观测性和敏感信息治理

- 优先级：`P1`
- 状态：`TODO`
- 目标：保留排障所需 trace 和指标，同时避免模型输入、ASR transcript、TTS 文本和用户资料泄露。
- 影响范围：`core/observability.py`、LangSmith 配置、日志、配置中心和运维告警。
- 实施要点：
  - 对手机号、地址、用户资料、订单信息、ASR 文本和模型提示词建立脱敏策略。
  - 区分开发、测试、生产的 trace 字段、采样率、访问权限和保留周期。
  - 增加模型调用耗时、失败率、token/费用、ASR/TTS 延迟、推荐空结果率和订单失败率指标。
  - 追踪系统继续保持 fail-open，但业务日志必须保留可关联的 request/turn ID。
- 验收标准：生产 trace 不包含明文敏感字段；超过成本或失败率阈值能触发告警；关闭 LangSmith 时核心业务仍可用；排查单个 turn 时可以串起 API、Agent、数据库和实时事件。

### TASK-006：增强实时事件和多实例会话可靠性

- 优先级：`P1`
- 状态：`TODO`
- 目标：明确 Redis 短期重放的边界，并支持多 API 实例下的会话串行和断线恢复。
- 影响范围：`realtime/hub.py`、`realtime/router.py`、Redis 配置、session lock、事件存储和前端 resume 逻辑。
- 实施要点：
  - 明确事件 TTL、最大条数、客户端 `afterSeq` 过期后的补偿策略。
  - 使用跨实例可见的发布/订阅和会话锁，确保同一 session 不会并行处理冲突 turn。
  - 为文本事件保留唯一序号和幂等消费语义；音频二进制继续明确不支持断点续播。
  - 对锁超时、Redis 不可用、重复提交和连接重建增加可观测日志及降级策略。
- 验收标准：单实例和多实例下事件顺序一致；断线后不会重复发送已确认事件；重放窗口过期时客户端收到明确的重新开始提示；同一 session 的并发 turn 只能有一个进入业务执行。

### TASK-007：建立稳定的 CI 和集成测试环境

- 优先级：`P1`
- 状态：`TODO`
- 目标：让完整测试在干净环境中可重复运行，消除本地 Windows/Python 版本差异导致的 asyncpg 跨事件循环问题。
- 影响范围：`apps/api/pyproject.toml`、测试 fixture、CI workflow、PostgreSQL/PGVector/Redis 服务定义。

  - 在 CI 中执行类型检查、构建、lint、单元测试和标记后的集成/E2E 测试。
- 验收标准：干净环境可一次完成规定测试命令；失败测试能明确归因于代码、基础设施或外部模型；测试数据不会污染开发库；至少保留推荐、订单、实时语音和权限边界的回归用例。

## 7. 推荐执行顺序

1. 先完成 `TASK-001`，建立所有后续生产任务的身份和权限前提。
2. 并行推进 `TASK-003`、`TASK-004` 和 `TASK-005`，分别处理扩展性、配置治理和运维安全。
3. 在多实例部署前完成 `TASK-006`，在正式上线前完成 `TASK-007` 并将其作为发布门禁。
4. 每个任务完成后同步更新需求、架构、实现和本文状态，并补充对应测试与运行手册。

## 8. 通用完成定义

一个任务只有同时满足以下条件才可标记为 `DONE`：

- 代码实现符合需求和架构边界，未绕过服务端事实校验。
- 关键正常、异常、降级和权限路径有自动化测试。
- 配置、数据库变更、API/WS 契约和前端行为已同步更新。
- 文档记录了影响范围、运行方式、失败处理和回滚策略。
- 通过适用的类型检查、构建、lint、单元测试和集成测试。
